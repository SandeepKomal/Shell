Running scripts

command not found

./deploy.sh: line 5: ehco: command not found

Symptom

A script or the terminal stops on a word it cannot run. The exit status is 127.

Why it happens

Bash looked for a function, a builtin and then a program with that name in every directory of $PATH, and found none.

  • A typo in the command name
  • The program is installed outside $PATH (for example /usr/local/bin under cron)
  • Spaces around = in an assignment: NAME = value runs a command called NAME
  • A script in the current directory run without ./
  • A function defined in your terminal, which child scripts never see

Confirm

type -a <name>
echo "$PATH"
command -v <name> || echo missing

Fix

Correct the name, install the program, call it by its full path, or set PATH at the top of the script. For assignments, remove the spaces: NAME=value.

Prevent

Set PATH explicitly in scripts that run from cron or CI, and check required tools up front with command -v.

Permission denied

bash: ./report.sh: Permission denied

Symptom

Running a script by its path fails at once with exit status 126.

Why it happens

The file exists but is not executable for you, or a directory on its path cannot be entered.

  • The script has no execute bit (-rw-r--r--)
  • The file system is mounted noexec, as /tmp often is
  • A fixed file name in the shared /tmp that another user's job created first
  • Writing to a file the shell cannot open, such as sudo echo x > /etc/file (the redirection runs as you)

Confirm

ls -l <script>
findmnt -no OPTIONS --target <script>
id

Fix

chmod +x script.sh. For noexec mounts run bash script.sh or move the script. For root-owned files use echo x | sudo tee /etc/file.

Prevent

Commit scripts with the execute bit (git update-index --chmod=+x) and keep them out of /tmp.

No such file or directory

/opt/tools/report.sh: line 2: ./lib/common.sh: No such file or directory

Symptom

A script, source, cd or a redirection fails on a path that you can see exists.

Why it happens

The path is resolved from the current directory, which is not the one you expect, or the name has invisible characters or spaces.

  • A relative path, run from cron or another directory
  • An unquoted path with spaces split into several arguments
  • A carriage return at the end of the name from a Windows file
  • The parent directory of a redirection does not exist
  • A glob that matched nothing, passed on literally (*.log)

Confirm

pwd
ls -l -- "<path>"
printf '%q\n' "<path>"

Fix

Use absolute paths, or build them from the script's directory: $(dirname "${BASH_SOURCE[0]}"). Quote paths. Strip \r from data files.

Prevent

Start scripts with cd "$(dirname "${BASH_SOURCE[0]}")" || exit 1 when they rely on neighbouring files, and use shopt -s nullglob before looping over globs.

cannot execute: required file not found

bash: ./deploy.sh: cannot execute: required file not found

Symptom

A script that exists and is executable fails immediately with exit status 127. Older bash says /bin/bash^M: bad interpreter: No such file or directory; env says /usr/bin/env: 'bash\r': No such file or directory.

Why it happens

The interpreter named on the #! line does not exist. Almost always the line ends with a Windows carriage return, so the kernel looks for /bin/bash\r.

  • The file was saved with CRLF line endings
  • The #! line names an interpreter that is not installed, such as /bin/zsh
  • A typo in the #! path

Confirm

head -1 <script> | cat -A
file <script>

Fix

Convert the line endings: sed -i 's/\r$//' script.sh or dos2unix script.sh.

Prevent

Add *.sh text eol=lf to .gitattributes and set your editor to LF for scripts.

$'\r': command not found

deploy.sh: line 2: $'\r': command not found

Symptom

bash script.sh prints $'\r': command not found on blank lines, and syntax error near unexpected token $'do\r''.

Why it happens

Every line ends with a carriage return, which bash treats as part of the last word.

  • The file was edited on Windows or copied from a web page

Confirm

cat -A <script> | head
file <script>

Fix

sed -i 's/\r$//' script.sh, then run it again.

Prevent

.gitattributes with *.sh text eol=lf.

[[: not found

/home/dev/report.sh: 3: [[: not found

Symptom

A bash script fails under cron, sh script.sh or a Docker CMD, with errors such as [[: not found, source: not found, [: x: unexpected operator or Bad substitution.

Why it happens

The script is running in sh (dash on Debian and Ubuntu, busybox ash on Alpine), which lacks bash features.

  • No #! line, so /bin/sh runs it
  • Running it as sh script.sh, which ignores the #! line
  • #!/bin/sh on a script that uses bash features

Confirm

head -1 <script>
ls -l /bin/sh

Fix

Start with #!/usr/bin/env bash and run the file directly (./script.sh), or write POSIX sh only.

Prevent

Always write a #! line; check sh scripts with checkbashisms or ShellCheck's --shell=sh.

Argument list too long

bash: /usr/bin/rm: Argument list too long

Symptom

rm *.log, cp * or grep x * fail in a directory with many files.

Why it happens

The glob expanded to more text than the kernel allows for one program's arguments.

  • Tens of thousands of matching files

Confirm

ls | wc -l
getconf ARG_MAX

Fix

Let find do it: find . -name '*.log' -delete, or find . -name '*.log' -print0 | xargs -0 rm --.

Prevent

Use find for bulk operations on directories that grow.

Syntax

syntax error near unexpected token

deploy.sh: line 9: syntax error near unexpected token `fi'

Symptom

The script stops before running the command at that line, with exit status 2.

Why it happens

Bash read a word or operator where its grammar does not allow one. The real mistake is often a line or two earlier.

  • A missing then, do, ; or ;;
  • A missing space: if [$x = 1] or } without a ; before it
  • Windows line endings ($'do\r')
  • A function written as function name() { in sh

Confirm

bash -n <script>
cat -A <script> | sed -n '1,12p'

Fix

Look at the named line and the one before it; add the missing keyword, space or separator.

Prevent

Run bash -n and ShellCheck in CI on every script.

Now learn it: break and fix it yourself in cannot execute: required file not found, then take Level 11 · Debugging. Open in Troubleshoot

syntax error: unexpected end of file

deploy.sh: line 14: syntax error: unexpected end of file

Symptom

The error points at the last line of the script.

Why it happens

Something opened was never closed: if without fi, do without done, { without }, or a here-document without its end marker.

  • A missing fi, done, esac or }
  • A here-document whose end marker is indented or has trailing spaces
  • } on the same line as a command without ;

Confirm

bash -n <script>
grep -nE '^\s*(if|fi|for|while|do|done|case|esac)\b' <script>

Fix

Find the block that is not closed and close it. Put here-document end markers at the start of the line (or use <<- with tabs).

Prevent

Indent consistently so open blocks are visible, and run bash -n in CI.

Now learn it: take Level 11 · Debugging. Open in Troubleshoot

unexpected EOF while looking for matching

deploy.sh: line 3: unexpected EOF while looking for matching `"'

Symptom

The script stops with exit status 2; lines after the quote never run.

Why it happens

A quote, $(, or backtick was opened and never closed before the end of the file.

  • An unbalanced " or '
  • An apostrophe inside single quotes: 'it's'
  • A $( without its )

Confirm

bash -n <script>
grep -n "'" <script>

Fix

Close the quote. For an apostrophe inside single quotes write 'it'\''s', or use double quotes.

Prevent

An editor with syntax highlighting shows the unclosed string at once.

Variables

unbound variable

./sync.sh: line 3: DEBUG: unbound variable

Symptom

With set -u the script exits with status 1 as soon as it reads a variable that was never set.

Why it happens

set -u (nounset) makes reading an unset variable an error, which ends a non-interactive shell.

  • An optional variable with no default
  • A missing argument: $1 when the script was run with none
  • A typo in a variable name
  • A variable set in your login shell but not under cron or CI

Confirm

declare -p <NAME>
env | grep <NAME>

Fix

Give optional variables a default with ${NAME:-default}, require others with ${NAME:?message}, and fix typos.

Prevent

Keep set -u: it finds typos. Document required variables at the top of the script.

parameter null or not set

./migrate.sh: line 2: DEPLOY_ENV: DEPLOY_ENV is not set

Symptom

The script stops with status 1 and prints a variable name followed by a message.

Why it happens

A ${NAME:?message} guard found the variable empty or unset. This is the guard working.

  • The variable was not passed in, or not exported by the parent script
  • A missing command-line argument (${1:?usage})

Confirm

env | grep <NAME>
declare -p <NAME>

Fix

Pass the value: export NAME=value in the caller, or NAME=value ./script.sh.

Prevent

Keep the guard; add a usage message so the next person knows what to pass. If the message comes from a here-document, quote its delimiter (<<'EOF').

bad substitution

./report.sh: 4: Bad substitution

Symptom

A ${...} expansion fails. In dash the message is Bad substitution with a capital B.

Why it happens

The shell does not understand that form of ${...}: either it is a bash feature running in sh, or it is mistyped.

  • Bash-only forms like ${var//a/b} or ${var^^} run by sh (no #! line, or sh script.sh)
  • A typo such as ${x!} or a space inside the braces

Confirm

head -1 <script>
ls -l /bin/sh

Fix

Run the script with bash: #!/usr/bin/env bash and ./script.sh, not sh script.sh. Correct the expansion.

Prevent

Start every script with a #! line for the shell you write for.

readonly variable

./deploy.sh: line 8: ENV: readonly variable

Symptom

An assignment fails with status 1 and the old value stays.

Why it happens

The variable was made read-only with readonly or declare -r, often in a sourced settings file.

  • A library or env file marks settings readonly
  • Assigning to bash's own read-only variables such as UID

Confirm

declare -p <NAME>

Fix

Use another name, or set the value before it is made read-only.

Prevent

Do not reuse names like UID, PWD or PATH for your own data.

not a valid identifier

./env.sh: line 2: export: `DB-HOST=db.internal': not a valid identifier

Symptom

export, read, local or unset rejects a name.

Why it happens

Variable names may contain only letters, digits and underscores, and cannot start with a digit.

  • A dash in a name, as in DB-HOST
  • A $ before the name: read $name
  • Spaces around = with export: export A = 1

Confirm

grep -n 'export\|read' <script>

Fix

Use a valid name (DB_HOST) and no $ where you assign or read into a variable.

Prevent

Use UPPER_SNAKE_CASE for environment variables.

Words no longer split after changing IFS

restart-svc: unknown service 'nginx redis worker'

Symptom

After some CSV parsing, a list of names arrives as one word, or paths are split at commas.

Why it happens

IFS=, on its own line changes word splitting for the rest of the script: spaces stop separating words.

  • IFS=, (or IFS=$'\n') set globally to parse one line
  • Forgetting to restore IFS

Confirm

printf '%q\n' "$IFS"

Fix

Set IFS only for the command that needs it: IFS=, read -r a b <<< "$line". Use arrays for lists.

Prevent

Never change IFS globally; if you must, do it in a function with local IFS.

Tests

unary operator expected

./health.sh: line 3: [: !=: unary operator expected

Symptom

An if [ ... ] prints this error and takes the else branch (status 2), so alerts and checks silently do nothing.

Why it happens

An unquoted variable was empty, so it vanished: [ $x != ok ] became [ != ok ].

  • An unquoted empty variable inside [ ]
  • A command substitution that printed nothing

Confirm

declare -p <NAME>
bash -x <script>

Fix

Quote the variable: [ "$x" != ok ], or use [[ $x != ok ]].

Prevent

Quote every expansion inside [ ], or prefer [[ ]] in bash scripts. The same mistake makes [ -n $var ] true when var is empty.

binary operator expected

./watch.sh: line 2: [: -q: binary operator expected

Symptom

An if [ ... ] prints an error and is treated as false. With four or more words the message is a syntax error naming the unexpected word instead.

Why it happens

[ received words it cannot read as a test: usually a command put inside the brackets, or a value with spaces.

  • if [ grep -q x file ]: a command inside [ ]
  • An unquoted variable with spaces in it

Confirm

bash -x <script>

Fix

Run the command directly: if grep -q x file; then. Quote variables: [ "$a" = "$b" ].

Prevent

Remember that [ is the test command, not grouping.

too many arguments

./check.sh: line 4: [: too many arguments

Symptom

A test fails with status 2 when a value has spaces or matches several files.

Why it happens

An unquoted variable split into several words, or a glob expanded to several file names, inside [ ] or cd.

  • [ $name = x ] where name has spaces
  • [ -f *.log ] with more than one log file
  • cd $dir with spaces in the path

Confirm

declare -p <NAME>
bash -x <script>

Fix

Quote: [ "$name" = x ]. To test for any matching file use compgen -G '*.log' or a loop.

Prevent

Quote every variable you did not intend to split.

integer expression expected

./disk.sh: line 3: [: 100%: integer expression expected

Symptom

A numeric test errors and is treated as false; thresholds never trigger.

Why it happens

-gt, -lt, -eq and friends need plain integers. The value has a unit, a decimal point, spaces or a \r.

  • A percentage or unit from df, free -h or du -h
  • A decimal such as load average 1.52
  • An empty value
  • A carriage return from a Windows file

Confirm

printf '%q\n' "$value"

Fix

Strip units first: v=${v%\%}; use awk for decimals; give empty values a default. Do not switch to >, which compares text (100 sorts before 90).

Prevent

Ask tools for raw numbers (df -P, --output, -b) rather than human-readable ones.

Arithmetic

syntax error: operand expected

./report.sh: line 6: 91%: syntax error: operand expected (error token is "%")

Symptom

An arithmetic expansion fails and bash abandons the rest of that command line.

Why it happens

The text inside $(( )), (( )) or a variable used there is not a valid number or expression.

  • A value with a unit, such as 91%
  • An empty operand: $(( 3 + ))
  • A variable holding text

Confirm

printf '%q\n' "$value"

Fix

Clean the value before using it in arithmetic, and give empty values a default: $(( ${n:-0} + 1 )).

Prevent

Validate numbers: [[ $n =~ ^[0-9]+$ ]] || exit 2.

value too great for base

./rotate.sh: line 4: 08: value too great for base (error token is "08")

Symptom

Arithmetic on dates or times works most of the month, then fails on the 8th or 9th, or at 08:00.

Why it happens

A leading zero makes bash read the number as octal, where 8 and 9 do not exist.

  • $(date +%m), %d or %H used in arithmetic

Confirm

echo $(( 07 )) $(( 010 ))

Fix

Force base 10: $(( 10#$month + 1 )), or ask date for no padding: date +%-m.

Prevent

Always use 10# on zero-padded numbers.

division by 0

./stats.sh: line 7: total / count: division by 0 (error token is "count")

Symptom

An average or percentage fails on an empty input.

Why it happens

The divisor evaluated to 0, often because a count was empty.

  • No matching lines, so the count is 0
  • An unset variable, which arithmetic treats as 0

Fix

Handle the empty case explicitly in reports.

Symptom

A sed s/.../.../ command fails when a variable is involved.

The pattern or replacement contains the delimiter, usually / from a path or URL, which ends the command early.

Jobs and signals

A failed background job did not fail the script

upload-region: us: 403 Forbidden ... and the script exits 0

Symptom

Jobs started with & fail, yet the script reports success and exits 0, even with set -e.

Why it happens

A background job's exit status only comes back through wait PID or wait -n. wait with no arguments always returns 0, and set -e never sees background jobs.

  • cmd & ... wait with no PIDs
  • Not saving $! after each job
  • Expecting set -e to cover jobs

Confirm

cmd & p=$!; wait "$p"; echo $?
jobs -l

Fix

Save each PID (pids+=($!)) and wait for each one: for p in "${pids[@]}"; do wait "$p" || failed=1; done, then exit non-zero if any failed.

Prevent

Never use bare wait where failures matter; for many jobs use xargs -P, whose exit status (123) reports a failure.

wait: pid is not a child of this shell

./run.sh: line 7: wait: pid 4123 is not a child of this shell

Symptom

wait returns 127 straight away.

Why it happens

A shell can only wait for processes it started itself. The PID belongs to another shell, a subshell, or a process started by a different script.

  • The job was started inside ( ), a pipeline or $( ), so a subshell owns it
  • The PID came from a file or from pgrep
  • The job was already waited for

Confirm

jobs -l
echo $!

Fix

Start the job in the same shell that waits for it, and keep $! right after starting it. To wait for an unrelated process, poll with while kill -0 "$pid"; do sleep 1; done.

Prevent

Keep job control in one place: start, record and wait in the same function.

Terminated

Terminated

Symptom

A script or job stops part way and the shell prints Terminated (exit status 143), Hangup (129) or Killed (137).

Why it happens

A signal ended it: TERM from kill, systemctl stop or timeout; HUP when the terminal or SSH session went away; KILL from the OOM killer or kill -9. Its cleanup only ran if it had a trap.

  • systemd stopping or restarting the service
  • The SSH session ending for a job started with &
  • A timeout limit
  • The out-of-memory killer (Killed, 137)

Confirm

journalctl -u <service> | tail
dmesg | grep -i 'killed process'
echo $?

Fix

Clean up in trap '...' EXIT (bash runs it on TERM, HUP and INT too), run long work with nohup, setsid, tmux or a systemd unit, and give it the memory it needs.

Prevent

Assume any script can be stopped at any line: register cleanup as soon as you create something, and make reruns safe.

Exit status 124 from timeout

curl: (28) Operation timed out after 10000 milliseconds with 0 bytes received

Symptom

A command run under timeout ends with status 124, or curl reports (28) Operation timed out; or, without a limit, a cron job never finishes and copies pile up.

Why it happens

The command took longer than its limit. timeout sent it TERM and returned 124; curl -m gave up with 28. Without a limit, network calls can wait for a very long time.

  • A server that accepts connections and never answers
  • A limit shorter than the work needs
  • No limit at all, so the job hangs

Confirm

time <command>
timeout 10 <command>; echo $?

Fix

Give every network call a limit (timeout 10 cmd or curl -m 10) and treat 124 as a failure: || { echo 'timed out' >&2; exit 1; }.

Prevent

Put a time limit on everything a cron job calls, and on the job itself.

Exit status

What does exit status 126, 127, 130 or 137 mean?

(echo $? prints 1, 2, 126, 127, 128+n)

Symptom

A job failed with a number and no message.

Why it happens

0 is success; 1 a general error; 2 misuse or a syntax error; 126 found but not executable; 127 not found; 128+n killed by signal n: 130 Ctrl+C, 137 SIGKILL (often the OOM killer), 143 SIGTERM.

  • See the specific error entries above for 126 and 127
  • 137 in containers usually means the memory limit was hit

Confirm

echo $?
dmesg | grep -i 'killed process'

Fix

Act on the meaning: permissions for 126, PATH for 127, memory for 137.

Prevent

Have scripts exit with documented codes (0 ok, 1 failure, 2 bad usage).

Script exits silently with set -e

(no message; exit status 1)

Symptom

A script with set -e stops part way with no error message.

Why it happens

Some command returned non-zero and set -e ended the script. The command itself printed nothing.

  • grep found nothing (status 1)
  • (( count++ )) or let when the value was 0
  • [ cond ] && action as the last line of a function, when cond is false
  • diff found differences

Confirm

bash -x <script> 2>&1 | tail -5
trap 'echo "failed at line $LINENO: $BASH_COMMAND" >&2' ERR

Fix

Add || true where failure is fine, use count=$((count + 1)), and write if cond; then action; fi instead of cond && action.

Prevent

Add an ERR trap that prints the line, so silent exits are never silent.

set -e did not stop the script

(the script reports success after a failure)

Symptom

A step failed, yet the script carried on and said it succeeded.

Why it happens

set -e ignores failures in many places: inside pipelines (except the last command), in if and while conditions, left of && and ||, in local x=$(cmd), and after cd that you did not check.

  • cmd | gzip > file without pipefail
  • local x=$(cmd) hiding cmd's status
  • $? read after another command
  • A failed cd followed by more commands

Confirm

echo "${PIPESTATUS[@]}"
bash -x <script>

Fix

Use set -euo pipefail, declare then assign (local x; x=$(cmd)), test commands directly with if, and cd dir || exit 1.

Prevent

Do not rely on set -e alone; check the steps that matter explicitly.

Cron and environment

Works in the terminal, fails from cron

(cron mails an error, or the job does nothing)

Symptom

A script works every time you run it, and fails when cron runs it.

Why it happens

Cron runs jobs with /bin/sh, PATH=/usr/bin:/bin, your home directory as the working directory, and none of your profile or .bashrc.

  • A program outside /usr/bin and /bin
  • Variables exported in .bashrc
  • Relative paths
  • No #! line, so sh runs it
  • % in the crontab line, which cron turns into a newline

Confirm

env -i HOME=$HOME PATH=/usr/bin:/bin /bin/sh -c '/path/to/script.sh'
grep CRON /var/log/syslog | tail

Fix

Set PATH in the script, load its own config by absolute path, use absolute paths, add a #! line, and escape % as \% in crontab.

Prevent

Test every cron job with env -i before adding it, and send its output to a log: >> /var/log/job.log 2>&1.

curl: (22) The requested URL returned error

curl: (22) The requested URL returned error: 503

Symptom

A download or API call fails in a script; also curl: (6) Could not resolve host and curl: (7) Failed to connect.

Why it happens

With -f, curl turns HTTP errors into exit status 22. 6 is DNS, 7 is a refused connection, 28 a timeout.

  • The server is down or busy (503)

  • A firewall or the service not listening
