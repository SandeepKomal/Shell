Running scripts

command not found

./deploy.sh: line 5: ehco: command not found

What it means

Bash tried to run the word at the start of the command. It looked for a function, then a builtin, then a program of that name in each directory of $PATH, and found none. ehco is the word it could not find; line 5 is where.

What you see

A script or the terminal stops on a word it cannot run. The exit status is 127.

Causes, most likely first

  1. A typo in the command name. Bash runs exactly the word you typed, so ehco is looked up as a program and not found.

    Check

    type -a <name>   # prints nothing: no function, builtin or program by that name anywhere
command -v <correct-name>   # prints a path: the program exists and the name was wrong

    Fix

    Correct the name.

  2. The program is installed outside $PATH (for example in /usr/local/bin when cron runs the script). The search only looks in the directories listed in $PATH, so a program elsewhere is invisible.

    Check

    echo "$PATH"   # the directories searched; compare with where the program lives
ls -l /usr/local/bin/<name> /opt/*/bin/<name> 2>/dev/null   # the program exists, just not in PATH

    Fix

    Call it by its full path, or set PATH at the top of the script: PATH=/usr/local/bin:/usr/bin:/bin. If it is not installed at all, install it.

  3. Spaces around = in an assignment: NAME = value. With spaces, bash reads NAME as a command and = and value as its arguments.

    Check

    grep -nE '^[[:space:]]*[A-Za-z_][A-Za-z0-9_]* +=' <script>   # a line here: an assignment with spaces

    Fix

    Remove the spaces: NAME=value.

  4. A script in the current directory run without ./. The current directory is not in $PATH, so deploy.sh is not found even when it is right there.

    Check

    ls -l ./<name>   # the file is here: run it as ./<name>

    Fix

    Run it as ./deploy.sh, or by its full path.

  5. A function defined in your terminal, which child scripts never see. Functions live in the shell that defined them; a script starts a new bash without them.

    Check

    type <name>   # 'is a function' in your terminal; run the same in the script with bash -c 'type <name>'

    Fix

    Put the function in a file and source it from the script, or turn it into a script on $PATH.

  6. The command runs under sudo, which replaces your PATH with its secure_path. The message then reads sudo: <name>: command not found.

    Check

    sudo printenv PATH   # the PATH sudo really uses; the program's directory is missing from it

    Fix

    Call the program by its full path under sudo, rather than widening secure_path.

Prevent

Set PATH explicitly in scripts that run from cron or CI, and check required tools up front with command -v.

Permission denied

bash: ./report.sh: Permission denied

What it means

Bash found the file but the kernel refused to run it as you. ./report.sh is the file it tried to run, and the exit status is 126: found but not executable. The cause is the file's mode, the mount it is on, or a directory on the way to it.

What you see

Running a script by its path fails at once with exit status 126.

Causes, most likely first

  1. The script has no execute bit (-rw-r--r--). The kernel only runs files marked executable for you.

    Check

    ls -l <script>   # no x in -rw-r--r--: this is your cause

    Fix

    chmod +x script.sh, and commit it with the bit: git update-index --chmod=+x script.sh.

  2. The file system is mounted noexec, as /tmp is on many hardened systems. On such a mount the kernel refuses to run any file, whatever its mode.

    Check

    findmnt -no OPTIONS --target <script>   # noexec in the list: this is your cause

    Fix

    Run it through the interpreter, bash script.sh, or move the script to a normal directory. Do not remount /tmp without noexec to make it work.

  3. A directory on the path cannot be entered. To reach a file you need x on every directory above it, so a locked parent gives the same error.

    Check

    namei -l <script>   # a directory without x for you on one of the lines: this is your cause

    Fix

    Ask the owner to grant access to that directory, or run the script from a place you can reach. Do not open it up with chmod 777.

  4. A fixed file name in the shared /tmp that another user's job created first. Your script then tries to write or run a file it does not own.

    Check

    ls -l /tmp/<name>   # owned by another user: this is your cause

    Fix

    Create temporary files with mktemp instead of a fixed name.

  5. Writing to a file the shell cannot open, such as sudo echo x > /etc/file. The redirection is done by your shell, as you, before sudo runs; the message then names the file, not the script.

    Check

    ls -l /etc/file   # owned by root, not writable by you: this is your cause

    Fix

    Let a root process open the file: echo x | sudo tee /etc/file > /dev/null.

Prevent

Commit scripts with the execute bit (git update-index --chmod=+x) and keep them out of /tmp.

No such file or directory

/opt/tools/report.sh: line 2: ./lib/common.sh: No such file or directory

What it means

A command was given a path that does not exist from where it is running. In the example, ./lib/common.sh is resolved from the current directory, not from the script's own directory, so the file is looked for in the wrong place.

What you see

A script, source, cd or a redirection fails on a path that you can see exists.

Causes, most likely first

  1. A relative path, run from cron or another directory. ./lib/common.sh means "in the current directory", which is wherever the script was started from.

    Check

    pwd   # in the script: not the script's directory means this is your cause
ls -l -- "<path>"   # works from the script's directory, fails from here

    Fix

    Build paths from the script's directory: here=$(dirname "${BASH_SOURCE[0]}"); source "$here/lib/common.sh", or use absolute paths.

  2. An unquoted path with spaces is split into several arguments. cat $file with My Report.txt asks for My and Report.txt, which do not exist.

    Check

    printf '[%s]\n' $file   # more than one line: the path was split

    Fix

    Quote it: cat -- "$file".

  3. A carriage return at the end of the name, from a Windows file. The name really is report.txt\r, which is not the file on disk.

    Check

    printf '%q\n' "<path>"   # ends in $'\r' or shows other hidden characters: this is your cause

    Fix

    Strip \r from the data file: sed -i 's/\r$//' list.txt.

  4. The parent directory of a redirection does not exist. > /var/log/app/run.log cannot create the file when /var/log/app is missing.

    Check

    ls -ld "$(dirname "<path>")"   # No such file or directory: create the directory

    Fix

    Create it first: mkdir -p /var/log/app.

  5. A glob that matched nothing is passed on literally. With no .log files, *.log stays as the text *.log, which is not a file.

    Check

    echo *.log   # prints *.log itself: nothing matched

    Fix

    Use shopt -s nullglob before looping over globs, so an empty match gives no words.

Prevent

Start scripts with cd "$(dirname "${BASH_SOURCE[0]}")" || exit 1 when they rely on neighbouring files, and use shopt -s nullglob before looping over globs.

cannot execute: required file not found

bash: ./deploy.sh: cannot execute: required file not found

What it means

The kernel was asked to start the file and could not find the interpreter it names on the #! line, or the loader a program needs. The file itself exists; something it depends on does not. The exit status is 127.

What you see

A script that exists and is executable fails immediately with exit status 127. Older bash says /bin/bash^M: bad interpreter: No such file or directory; env says /usr/bin/env: 'bash\r': No such file or directory.

Causes, most likely first

  1. The file was saved with CRLF line endings. The first line becomes #!/bin/bash\r, and there is no program called bash\r.

    Check

    head -1 <script> | cat -A   # ^M$ at the end: this is your cause

    Fix

    Convert the line endings: sed -i 's/\r$//' script.sh or dos2unix script.sh.

  2. The #! line names an interpreter that is not installed, such as /bin/zsh, or has a typo in its path. The kernel looks for exactly that path.

    Check

    head -1 <script>   # the path after #!
ls -l <that path>   # No such file or directory: install it or fix the line

    Fix

    Install the interpreter, or point #! at one that exists: #!/usr/bin/env bash.

  3. A program (not a script) whose dynamic loader is missing, such as a glibc build on Alpine (musl). The binary names its loader inside it, and that file does not exist here.

    Check

    file <program>   # 'interpreter /lib64/ld-linux-x86-64.so.2': check that this loader exists with ls -l

    Fix

    Use the build for this system's C library, such as a musl or static build on Alpine.

Prevent

Add *.sh text eol=lf to .gitattributes and set your editor to LF for scripts.

$'\r': command not found

deploy.sh: line 2: $'\r': command not found

What it means

Bash read a carriage return (\r, shown as $'\r') as part of a word. Every line of the file ends with \r\n instead of \n, so a blank line becomes a command called \r.

What you see

bash script.sh prints $'\r': command not found on blank lines, and syntax error near unexpected token $'do\r''.

Cause

  1. The file was edited on Windows or copied from a web page. Those save lines with CRLF endings, and bash only strips the LF.

    Check

    cat -A <script> | head   # ^M$ at the end of lines: this is your cause
file <script>   # 'with CRLF line terminators' says the same

    Fix

    sed -i 's/\r$//' script.sh, then run it again. Add *.sh text eol=lf to .gitattributes.

Prevent

.gitattributes with *.sh text eol=lf.

[[: not found

/home/dev/report.sh: 3: [[: not found

What it means

The script is running in sh, not bash. On Debian and Ubuntu sh is dash, on Alpine it is busybox ash, and they lack bash features. sh reports a missing feature as [[: not found or source: not found, with a bare line number after the script name.

What you see

A bash script fails under cron, sh script.sh or a Docker CMD, with errors such as [[: not found, source: not found, [: x: unexpected operator or Bad substitution.

Causes, most likely first

  1. No #! line, so /bin/sh runs it. Without one, the program that started it decides which shell runs it, and that is usually sh.

    Check

    head -1 <script>   # no #! line: this is your cause
ls -l /bin/sh   # -> dash: sh is not bash here

    Fix

    Start the script with #!/usr/bin/env bash and make it executable.

  2. Running it as sh script.sh. Naming the shell on the command line ignores the #! line. Docker's shell-form CMD and some cron lines do the same.

    Check

    grep -rn 'sh .*<script>' crontab Dockerfile 2>/dev/null   # sh <script> in how it is started

    Fix

    Run the file directly (./script.sh), or use bash script.sh. In a Dockerfile use the exec form: CMD ["./script.sh"].

  3. #!/bin/sh on a script that uses bash features. The line asks for sh, and sh is not bash.

    Check

    shellcheck --shell=sh <script>   # lists the bash-only lines

    Fix

    Change the line to #!/usr/bin/env bash, or rewrite those lines in POSIX sh.

Prevent

Always write a #! line; check sh scripts with checkbashisms or ShellCheck's --shell=sh.

Argument list too long

bash: /usr/bin/rm: Argument list too long

What it means

The kernel refused to start the program because its arguments and environment together are larger than it allows (E2BIG). The message names the program, here /usr/bin/rm; usually a glob such as *.log expanded to too many names.

What you see

rm *.log, cp * or grep x * fail in a directory with many files.

Causes, most likely first

  1. Tens of thousands of matching files. Every file name becomes one argument.

    Check

    ls | wc -l   # tens of thousands: this is your cause
getconf ARG_MAX   # the limit, in bytes

    Fix

    Let find do it: find . -name '*.log' -delete, or find . -name '*.log' -print0 | xargs -0 rm --.

  2. A very large environment, which counts against the same limit. Even a short command fails when the environment is huge.

    Check

    env | wc -c   # size of the environment in bytes, without printing it; a large share of ARG_MAX is your cause

    Fix

    Find what fills it (often a variable that holds a whole file) and stop exporting it.

  3. One argument longer than 128 KiB on Linux (MAX_ARG_STRLEN), such as a whole file passed with "$(cat file)". Each single argument has its own limit, separate from the total.

    Check

    wc -c < <file>   # over 131072: too big for one argument

    Fix

    Pass the file name or feed it on standard input instead: cmd < file.

Prevent

Use find for bulk operations on directories that grow.

cannot execute binary file: Exec format error

bash: ./node_exporter: cannot execute binary file: Exec format error

What it means

The kernel opened the file and could not recognise it as a program it can run: it is built for another CPU architecture, is not a program at all, or is a script without a #! line started by something other than a shell. The exit status is 126.

What you see

A downloaded program fails at once with exit status 126, or a container stops at start with exec /usr/local/bin/entrypoint.sh: exec format error in its log.

Causes, most likely first

  1. A binary for another architecture: amd64 on an arm64 host, or the reverse, such as an image built on an Apple silicon Mac and run on an x86 server.

    Check

    file <program>   # ARM aarch64 or x86-64: compare with the next line
uname -m   # x86_64 or aarch64: a mismatch is your cause

    Fix

    Use the build for this machine's architecture, or build images for the target with docker buildx build --platform linux/amd64.

  2. The download saved an HTML error page or an archive instead of the program.

    Check

    head -c 64 <program> | od -c | head -3   # <html or a gzip header instead of ELF: this is your cause

    Fix

    Download it again with curl -fL, and check it against its published checksum.

  3. A container entrypoint script with no #! line, or a blank line or byte-order mark before it. Docker runs the entrypoint directly, with no shell to fall back on.

    Check

    head -c 64 <script> | od -c | head -3   # the first two bytes are not # !

    Fix

    Make #!/usr/bin/env bash the very first line.

Prevent

Pick release files by uname -m in install scripts, check downloads against their published checksum, and build images for every platform you run.

declare: -A: invalid option (bash 3.2 on macOS)

./sync.sh: line 3: declare: -A: invalid option

What it means

macOS ships bash 3.2 as /bin/bash. Associative arrays (declare -A), mapfile, case conversion and other features arrived in bash 4, so 3.2 rejects them: -A is an invalid option, mapfile is not found, ${name,,} is a bad substitution.

What you see

A script that works on Linux fails on a Mac: declare -A is an invalid option, mapfile is not found, and ${name,,} is a bad substitution.

Causes, most likely first

  1. #!/bin/bash runs the system bash 3.2 even when a newer bash is installed.

    Check

    head -1 <script>   # #!/bin/bash: the system 3.2
/bin/bash --version | head -1   # version 3.2: this is your cause

    Fix

    Install a current bash (brew install bash) and start the script with #!/usr/bin/env bash.

  2. A newer bash from Homebrew is in $PATH, but the script is run as bash script.sh from a shell where it is not.

    Check

    type -a bash   # /bin/bash listed first in that shell

    Fix

    Put Homebrew's bin directory first in PATH, or run the script directly. If it must run on a stock Mac, keep to bash 3.2 features.

Prevent

Scripts that need bash 4 can say so at the top: ((BASH_VERSINFO[0] >= 4)) || { echo 'needs bash 4 or newer' >&2; exit 1; }.

No space left on device

cp: error writing '/var/backups/db.sql': No space left on device

What it means

A write failed because the file system has no free blocks, or no free inodes (the per-file records a file system has a fixed number of). The message names the file being written. Bash writes here-documents to a temporary file, so they fail too.

What you see

Writes fail part way: a backup or log stops growing, cp or tar exits non-zero, and even small scripts fail with cannot create temp file for here-document.

Causes, most likely first

  1. Logs or old backups filled the disk.

    Check

    df -h <path>   # Use% 100
du -xh --max-depth=1 <path> | sort -h | tail   # the directory that holds the space

    Fix

    Rotate or compress logs and remove old backups, then keep a fixed number (scripts/backup_rotate.sh -k).

  2. A deleted file is still open in a running process, so its space is not freed. df counts it, du does not.

    Check

    lsof +L1   # deleted files still open, with their size and process

    Fix

    Restart the process that holds it (scripts/deleted_open_files.sh lists them), or truncate it through /proc/<pid>/fd/<n>.

  3. Millions of small files used up the inodes while df -h still shows free space.

    Check

    df -i <path>   # IUse% 100: inodes, not bytes

    Fix

    Find the directory with the many small files (du --inodes -x <path> | sort -n | tail) and clean it up.

  4. On ext4, the blocks reserved for root (5% by default): Avail is 0 for other users while Used is below Size.

    Check

    df -h <path>   # Avail 0 but Used below Size: the reserved blocks

    Fix

    Free space as above. Do not just lower the reservation; it is what lets root recover a full disk.

  5. A large write to a small /tmp.

    Check

    df -h /tmp   # a small tmpfs

    Fix

    Write large temporary files elsewhere: TMPDIR=/var/tmp.

Prevent

Alert on disk and inode use well before 100%, rotate logs, and keep a fixed number of backups (scripts/backup_rotate.sh -k).

Syntax

syntax error near unexpected token

deploy.sh: line 9: syntax error near unexpected token `fi'

What it means

Bash was parsing the script and met a word or operator where its grammar does not allow one. It names the token it did not expect (fi here) and the line. Nothing in the script has run yet, and the real mistake is often a line or two earlier.

What you see

The script stops before running the command at that line, with exit status 2.

Causes, most likely first

  1. A missing then, do, ; or ;;. Without then, bash is still reading the condition when it reaches fi, which cannot appear there.

    Check

    bash -n <script>   # repeats the error without running anything
sed -n '<line-2>,<line>p' <script>   # look for the missing keyword just before the named line

    Fix

    Add the missing keyword or separator.

  2. A missing space, as in if [$x = 1], or } without a ; before it. Bash needs spaces to see [ and ] as words, and a ; or newline before a closing }.

    Check

    shellcheck <script>   # names the missing space or separator on that line

    Fix

    Add the space or the ;: if [ "$x" = 1 ]; then, { cmd; }.

  3. Windows line endings. The token is then shown as $'do\r' or similar: the \r makes do an unknown word.

    Check

    cat -A <script> | sed -n '1,12p'   # ^M$ at line ends: this is your cause

    Fix

    sed -i 's/\r$//' script.sh.

  4. An unquoted ( or ) in an argument, such as echo (beta). Parentheses are shell syntax, so bash reads them as the start of a subshell in the wrong place.

    Check

    grep -n '[^$]([^)]*)' <script>   # an unquoted ( in a command's arguments

    Fix

    Quote it: echo "(beta)".

Prevent

Run bash -n and ShellCheck in CI on every script.

syntax error: unexpected end of file

deploy.sh: line 14: syntax error: unexpected end of file

What it means

Bash reached the end of the script while a block was still open. It points at the last line because that is where it gave up; the block that was never closed starts earlier.

What you see

The error points at the last line of the script.

Causes, most likely first

  1. A missing fi, done, esac or }. Bash keeps reading for the closing word and finds the end of the file instead.

    Check

    bash -n <script>   # repeats the error without running anything
grep -nE '^\s*(if|fi|for|while|do|done|case|esac)\b' <script>   # count openers and closers; one more opener is your block

    Fix

    Close the block.

  2. A here-document whose end marker is indented or has trailing spaces. Bash never sees the marker, so the rest of the file becomes the here-document, and the block around it is never closed.

    Check

    grep -n 'EOF' <script> | cat -A   # spaces before the marker or after it (before $): this is your cause

    Fix

    Put the end marker at the start of its line with nothing after it, or use <<- with tab indentation.

  3. } on the same line as a command without ;. Then } is read as an argument, and the function is never closed.

    Check

    grep -nE '[^;{ ] *}$' <script>   # a } with no ; before it

    Fix

    Add the separator: f() { cmd; }.

Prevent

Indent consistently so open blocks are visible, and run bash -n in CI.

unexpected EOF while looking for matching

deploy.sh: line 3: unexpected EOF while looking for matching `"'

What it means

A quote, $( or backtick was opened and never closed. Bash read to the end of the file looking for the matching character (shown in the message, here "). Exit status 2, and nothing after the quote runs.

What you see

The script stops with exit status 2; lines after the quote never run.

Causes, most likely first

  1. An unbalanced " or '. Bash treats everything after it as one long string.

    Check

    bash -n <script>   # repeats the error; the line it names is where the quote opened

    Fix

    Close the quote.

  2. An apostrophe inside single quotes: 'it's'. The apostrophe ends the string, and the final ' opens a new one that never closes.

    Check

    grep -n "'" <script>   # an odd number of ' on a line points to it

    Fix

    Write 'it'\''s', or use double quotes: "it's".

  3. A $( without its ). Bash keeps reading for the end of the command substitution.

    Check

    grep -n '\$(' <script>   # check each one has its )

    Fix

    Add the closing ).

Prevent

An editor with syntax highlighting shows the unclosed string at once.

event not found

-bash: !word: event not found

What it means

In an interactive shell, ! starts history expansion: !word means "the last command starting with word". Bash found no such command, so it refused the line before running it. Scripts run with history expansion off, which is why the same line works there.

What you see

A command typed in the terminal with ! in it fails before it runs, such as echo "Pa55!word". The same line works in a script.

Causes, most likely first

  1. ! inside double quotes in a typed command. Double quotes do not stop history expansion.

    Check

    set -o | grep histexpand   # histexpand on: this shell expands !

    Fix

    Use single quotes ('Pa55!word') or escape the ! with a backslash.

  2. A password or message containing ! pasted into the terminal.

    Check

    set -o | grep histexpand   # on in your terminal

    Fix

    Turn history expansion off for the session with set +H, and keep passwords off the command line altogether.

Prevent

Single-quote literal strings, and keep passwords off the command line altogether.

Variables

unbound variable

./sync.sh: line 3: DEBUG: unbound variable

What it means

The script read a variable that was never set, and set -u (nounset) makes that an error. DEBUG is the variable; a non-interactive shell exits with status 1 on the spot.

What you see

With set -u the script exits with status 1 as soon as it reads a variable that was never set.

Causes, most likely first

  1. An optional variable with no default. Without a default, reading it when nobody set it is an error under set -u.

    Check

Causes, most likely first

  1. sshd is stopped or listens on another port (refused).

    Check

    nc -vz -w 5 <host> 22   # refused: nothing listens on 22
ssh -v -o ConnectTimeout=5 <user>@<host> true   # 'Connection refused' after 'Connecting to'

    Fix

    Start sshd on the host (through the console), or connect to the right port with -p.

  2. A firewall or security group drops port 22 from where you are (timed out), or a host firewall rejects it (refused or no route to host).

    Check

    nc -vz -w 5 <host> 22   # timed out: dropped; compare with a host that works from the same place

    Fix

    Allow port 22 from your address only, or go through the bastion.

  3. The host is down, or its name points at an old address.

    Check

    getent hosts <host>   # the address ssh will use; compare with the inventory

    Fix

    Fix the DNS record or the inventory, or start the host.

  4. Connecting to a private address from outside the network.

    Check

    getent hosts <host>   # 10.x, 172.16-31.x or 192.168.x from outside

    Fix

    Connect through the VPN or the bastion (ssh -J bastion <host>).

Prevent

Use -o ConnectTimeout=10 -o BatchMode=yes in loops so one host cannot stall the run, and report unreachable hosts apart from failed commands.

UNPROTECTED PRIVATE KEY FILE: permissions are too open

Permissions 0644 for '/home/deploy/.ssh/id_ed25519' are too open.

What it means

ssh refuses to use a private key that other users can read, and says so in a warning box. The message gives the file and its mode, here 0644 (readable by everyone). It then carries on without the key, which usually ends in Permission denied (publickey).

What you see

ssh prints a warning box, ignores the key, and then fails with Permission denied (publickey).

Causes, most likely first

  1. The key was copied or unpacked with default permissions (0644), or a CI job wrote it from a secret without setting its mode.

    Check

    stat -c '%a %U' <key>   # anything but 600 or 400, or another owner: this is your cause

    Fix

    chmod 600 <key> and chmod 700 ~/.ssh, owned by the user who runs ssh. In CI, write it with install -m 600.

  2. The key is on a mounted drive that does not keep Unix permissions, such as a Windows drive under WSL. chmod has no effect there.

    Check

    chmod 600 <key>; stat -c '%a' <key>   # still 777 or 644: the drive cannot keep the mode

    Fix

    Copy the key into ~/.ssh on the Linux file system and use it from there.

Prevent

Create key files with umask 077 or install -m 600, and keep them out of shared folders.

What it means

What you see

A reload changes nothing, or a restart takes the site down, after a config change.

  1. A typo, a missing semicolon, or a directive from a module that is not loaded.

    Check

    sudo nginx -t   # names the file and line of the parse error

terraform plan -detailed-exitcode exits 2

Error: Process completed with exit code 2.

What it means

With -detailed-exitcode, terraform plan exits 0 for no changes, 1 for an error and 2 for "the plan has changes". Terraform worked; the script or CI treated 2 as a failure like 1.

What you see

A drift check or CI job using -detailed-exitcode fails, or pages on-call, whenever there are changes, though Terraform itself worked.

Causes, most likely first

  1. The status is not captured, so set -e (or the CI step) stops the script on 2.

    Check

    terraform plan -detailed-exitcode -input=false > /dev/null; echo $?   # 2: changes, not an error

    Fix

    Capture the status and branch on it: rc=0; terraform plan -detailed-exitcode ... || rc=$?; case $rc in 0) ...;; 2) ...;; *) ...;; esac.

  2. if terraform plan ...; then sends drift to the error branch, because 2 is not 0.

    Check

    grep -n 'detailed-exitcode' <script>   # used inside if or with &&

    Fix

    Use the || rc=$? and case form. scripts/terraform_drift_check.sh reports 0, 1 drift and 2 error.

Prevent

Treat any multi-valued status (terraform, grep, diff) with || rc=$? and case. scripts/terraform_drift_check.sh reports 0, 1 drift and 2 error.

Error acquiring the state lock

Error: Error acquiring the state lock

What it means

Terraform takes a lock on the state before reading or writing it, so two runs cannot change it at once. It could not get the lock. When another run holds it, Terraform prints Lock Info: the lock ID, who holds it, the operation and when it was taken.

What you see

A plan or apply fails at once, naming a lock ID, who holds it and when it was taken.

Causes, most likely first

  1. Someone is applying right now, or a drift check or CI plan holds the lock while it runs.

    Check

    terraform plan -lock-timeout=60s   # succeeds after a wait: it was a run in progress

    Fix

    Wait, or use -lock-timeout.

  2. A run was killed and left a stale lock.

    Check

    aws dynamodb get-item --table-name <lock-table> --key '{"LockID":{"S":"<bucket>/<key>"}}'   # Info shows who holds it and since when (the <key>-md5 item is the state checksum, not the lock)
aws s3api head-object --bucket <bucket> --key <key>.tflock   # with use_lockfile = true (Terraform 1.10 and later)

    Fix

    Remove a lock with terraform force-unlock <ID> only after you know its run is dead.

  3. The lock call itself failed: no permission on the lock table (or the S3 lock file), or a wrong table name or region. The detail then shows an AWS error such as AccessDeniedException instead of Lock Info.

    Check

    aws sts get-caller-identity   # the identity Terraform runs as
aws dynamodb describe-table --table-name <lock-table> --region <region>   # ResourceNotFoundException: wrong name or region

    Fix

    Give that identity dynamodb:GetItem, PutItem and DeleteItem on the lock table only, or fix the backend's table name and region.

Prevent

Read-only checks such as drift detection can plan with -lock=false so they never block an apply; applies keep the lock.

Database backups readable by anyone on the host

-rw-r--r-- 1 postgres postgres 2.1G Oct 31 02:00 /var/backups/shop-20261031.sql.gz

What it means

Backup files can be read by more people than should. A backup holds every row of the database, so whoever can read it has all the personal data, without any of the application's access controls. The example -rw-r--r-- means anyone on the host can read it.

What you see

Backup files are world-readable, unencrypted, or copied to a bucket without encryption or with public access.

Causes, most likely first

  1. The default umask 022 creates files as 644.

    Check

    ls -l /var/backups/   # r for group or other: readable by others on the host

    Fix

    chmod 600 the files, and set umask 077 in the backup job.

  2. Off-site copies protected only by S3's default SSE-S3 (on for every new object since January 2023), which anyone who can read the bucket can still read, or copied to storage with no encryption at all.

    Check

    aws s3api get-bucket-encryption --bucket <bucket>   # AES256 is SSE-S3; aws:kms with your own key limits who can decrypt

    Fix

    Encrypt off-site copies with SSE-KMS under a key only the backup and restore roles can use, or client-side.

  3. A bucket policy or ACL that allows public or cross-account reads.

    Check

    aws s3api get-public-access-block --bucket <bucket>   # all four settings should be true

    Fix

    Block public access on the bucket and remove the grants.

  4. Old backups never deleted, so years of data sit in one place.

    Check

    ls -lt /var/backups/ | tail   # the oldest files and their dates

    Fix

    Delete backups beyond the retention period, and rotate in the job (scripts/backup_rotate.sh).

Prevent

Use backup scripts that set umask 077, encrypt uploads and rotate (scripts/pg_backup.sh, scripts/mysql_backup.sh, scripts/s3_backup_sync.sh).
